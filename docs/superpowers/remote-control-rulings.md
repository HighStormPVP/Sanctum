# Remote Control: decisions made during the build

Every decision the build controller made on the owner's behalf while building Remote Control, in the order made, copied from the build ledger. Each reads: what was decided, why, and what it costs if it turns out wrong. Later rulings that replace earlier ones say so.

1. Baseline committed on a new sanctum-fixes branch, not main, and nothing pushed — main stays as released and the owner's checkout keeps a stable copy — if wrong, a fast-forward merge to main fixes it.
2. Remote Control is built in a worktree — the owner's running Sanctum must not pick up half-built code — if wrong, only a directory location changes.
3. `playwright-core` is added as a devDependency in Task 8, the first task with e2e tests — the plan omits it — if wrong, one line moves.
4. `c.remoteControl` is defined in Task 9 and set directly in e2e tests until Task 11 adds the switch — needed before the UI exists — if wrong, tests need a helper.
5. `test/no-relay-address.test.js` excludes itself and test fixtures from its scan — otherwise it always fails on its own pattern — if wrong, one exclusion is too broad.
6. The Task 5 security review is dispatched by the controller, on the most capable model, after Task 5's task review — implementers don't dispatch reviewers — if wrong, a review is run at a different moment.
7. Task 1 uses 64 bytes of scrypt output for w — reducing a longer value modulo the group order reduces bias, and both sides only have to agree — if wrong, pairing still interoperates between our own devices, and a one-line change plus re-pairing fixes it.
8. Task 2 expands sharedKey with hkdf to a 32-byte key, exchanges the SPAKE2 confirmation MACs before anything else, and signs a transcript it builds itself from both pake messages — the plan omitted these — if wrong, Task 2's review catches it before any later task builds on it.
9. Task 2's exact flow written into the plan: confirmation MACs before use, hkdf to 32 bytes, signature over both pake messages — the original plan omitted them and RFC 9382 requires confirmation — if wrong, Task 5's security review catches it, and no user data exists yet.
10. miniflare moves from the root package to relay/package.json, with test:relay installing and running there — release CI runs npm ci on Node 20 and miniflare needs Node 22 and downloads binaries the app never ships — if wrong, relay tests need one more install step.
11. Task 5's session also produces a 4-byte connectionId from the handshake transcript, and the handshake messages travel beside the link, before it starts — Task 4's link needs an id both ends agree on, and the plan didn't assign one — if wrong, the manager derives the id differently.
12. Replayed hello is answered, and the replay fails at the auth step — a hello is unsigned so can't be told apart earlier, and no session completes — if wrong, nothing is exposed.
13. Laptop refuses a code that already failed on it, in Task 7 — closes the free guesses a fake home PC gets — if wrong, a retyped correct code needs a new one from home.
14. Authenticated heartbeat (15s, 45s timeout) plus restart on any decrypt throw or link overflow, in Task 7 — forged link headers can otherwise stall silently — if wrong, it costs a few messages and a reconnect.
15. After a guessed code, a man-in-the-middle is undetectable by protocol, so each device shows a fingerprint in Settings for comparison, with no required confirmation step — the owner asked for a code-only flow, and the odds are about 1 in 177 million per code — if wrong, a future required-compare step is small to add.
16. Home-side pairing entries stay provisional until the first session — a lost final message would otherwise leave a device that never connects — if wrong, a retry is needed.
17. Task 6's reopened items wait for Task 7's implementer rather than interrupting it — keystore.js isn't in Task 7's scope, and two writers could collide on the git index — if wrong, Task 7 builds on an interface that doesn't change.
18. Idle lock keeps keys in memory and allows reconnects; restart lock doesn't — the spec says the connection stays up and a locked laptop stays controllable, and a live session already holds the key — if wrong, a stolen running laptop keeps a connection, but the screen still needs the PIN.
19. A device acting only as a home PC has no user PIN and unlocks itself after a reboot, using a random secret sealed by the OS — the owner chose a PIN on the laptop, and an unattended home PC can't type one — if wrong, a copy of that PC's disk still needs its Windows login to unseal it, and a user PIN could be added later.
20. A device stuck by a damaged remote-autounlock.bin is treated as damage while protection is available: delete it, set the keys aside, start unpaired — no other way out exists, and the keys can't be opened anyway — if wrong, the owner pairs again.
21. The real PIN is set after pairing succeeds, with format checked first — a mistyped code on an unattended home PC shouldn't move it to the laptop rules — if wrong, a crash in that instant leaves a paired device on the sealed secret until needsPin prompts.
22. rtc signaling stays inside the link, in order — the reviewer showed it can't jump a queue with strict counters, and batched mirror traffic drains in about a second — if wrong, a busy connection stays on the relay longer than expected, with nothing lost.
23. Clicking Run on a code block in a shared chat on the laptop opens a confirmation showing the whole code before it runs, in Task 14 — the reviewer showed a home can hide a payload below the fold, and one click runs it — if wrong, it costs one extra click on the laptop.
24. agent fs tools (read_file, list_dir, grep) refuse Sanctum's own profile folder for every run, local or remote — a parent folder contains it, so refusing only in set-folder leaves the route open, and nothing legitimate needs it — if wrong, a local agent can't inspect its own logs and the owner must open them by hand.
25. large snapshots are paced by a per-part ack instead of a capped total — the owner asked for the laptop to see the chat exactly as at home, and a cap would hide big chats — if wrong, one extra frame type and slower snapshots on poor links.
26. no home-side dedupe of laptop sends; a late ok removes unchanged returned text, and the timeout message no longer claims the send failed — dedupe needs client-chosen message ids — if wrong, a person can still start a second run by resending changed text after a timeout, which could repeat tool actions in No-Approval. FINAL REVIEW should weigh.
27. every snapshot goes through the paced path with a byte window (at most 4 parts and 32 MiB in flight), one transfer at a time, restarts wait for outstanding parts, and a transfer with no progress for 10 minutes is dropped with a notice rather than ending the session — on 20-50 Mbit/s links the old re-ask overflowed the link and looped — if wrong, a slow first view of big chats and more protocol state.
28. the held-words cap changes from 2 MiB to 32 MiB per device, never evicting the newest — my 2 MiB ruling was wrong given a message can be 25 MiB — if wrong, up to 32 MiB of memory per offline laptop.
29. a page that has just loaded may restart a live transfer via reload:true on its first resync request, under the one-a-second limit — otherwise a reload that loses a part waits 10 minutes with no message — if wrong, a hostile laptop can restart its own transfer once a second, costing only its own bandwidth.
30. action frames are refused in manager.send while locked, idle-locked, or needsPin, and packaged builds lose DevTools for every user — the renderer was the only gate, and DevTools reached it — if wrong, public users can't open DevTools in a packaged build and the owner debugs from npm start. An idle-locked laptop's renderer still holds mirrored chats in memory; with DevTools gone a thief needs OS-level tools. FINAL REVIEW should weigh, and a real packaged run goes on Task 15's manual checks.
31. "Not now", "Remove <home> instead", closing the code dialog cancels the code, Devices tab showing without an address, and idle meaning no input anywhere in Sanctum are kept — reviewer found each acceptable, owner told and may overrule — if wrong, small UI changes.
32. my finding-5 ruling can strand typed words, since a laptop can't tell unshared from deleted. Next round adds a "Put in the message box" button on the notice, and words returned after their chat has gone use the same path instead of landing in the open box — never silently send-ready in the wrong chat, and never lost — if wrong, one extra button.
33. while locked, manager.send uses a closed allowlist on a plain JSON copy under 64 KiB, and a non-string type is refused at any time — a denylist was bypassed by a String object — if wrong, a frame a locked renderer needs gets refused and the laptop goes stale until unlock.
34. words whose chat has gone use one persistent bar with Put in the message box and Discard, memory only, at most 20 entries or 32 MiB — never lost, never send-ready without a person's choice — if wrong, one more UI element above the box, and words lost at restart.
35. a wipe or "Remove <home> instead" discards everything held during a lock — someone without the PIN must not see it — if wrong, the real owner who forgets the PIN loses words typed just before the lock.
36. openOnArrival expires after 30 s, and opens only with an empty box, nothing attached, and the same chat still open — a home chooses when a chat arrives — if wrong, a slow home's chat waits in the sidebar instead of opening.
37. a merge that would pass 32 MiB refuses the new words and keeps what's held, rather than dropping older words — keeps what the person typed first — if wrong, the newest words from a home are refused, which only a flood of over 32 MiB could cause.
38. tool calls keep running during an idle lock, per the spec's PIN section; tool-result and control-state join LOCKED_FRAMES_TO_HOME, tool-result capped at 8 MiB — otherwise commands hang while the laptop's screen is locked — if wrong, page code on a locked laptop could forge a tool result, and it needs DevTools to get there.
39. tool-call stays off LOCKED_FRAMES_TO_LAPTOP, tool-cancel joins it; a device with both roles that idle-locks gives its model a clear error for laptop tools — fails closed — if wrong, a long agent run on a both-roles device stops using its laptop's tools after 15 idle minutes.
40. in Approval Mode, commandAllowlist pre-approves only at home, and a call landing on a laptop always asks — the list is prefix-matched and predates a second machine, and spec line 188 promises pop-ups naming the machine — if wrong, extra pop-ups on a laptop until a per-device list exists.
41. silence ends the call for the model within 5 s but kills the laptop's command only on tool-cancel, a real session end, or 30 s of silence — spec line 182's 5 s is about telling the model — if wrong, a command can keep running up to 30 s after the model was told the laptop stopped answering, and a retry could overlap it.
42. refusals go to remote-refusals.log, collapsed per device per minute; remote-audit.log holds only what ran — a paired device could otherwise erase evidence — if wrong, one more file to read, and refusal detail is reduced to counts. This overrides notes ruling 1's naming of remote-audit.log for refusals.
43. a path not lexically inside an allowed folder is refused before canonicalizing; tool calls from a home PC can never use a network or device path — stops an SMB attempt from a steered model — if wrong, a laptop's NAS folder can't be used by a home model until a later change allows it.
44. a gap over 3.5 s that recovers still ends the live command, through home's tool-cancel — home has already told the model it failed, so running on would risk overlapping a retry — if wrong, short Wi-Fi gaps cost a long command; revisit after the real two-machine checks in Task 15.
45. a laptop MCP schema node with no determinable type, or an array with no items, drops the tool; anyOf and oneOf flatten to the first non-null branch — one laptop's tool mustn't break every Gemini request at home — if wrong, some honest tools with Any parameters aren't offered, with a toast saying so. No live API call backs this; Task 15 asks the owner.
46. an approval over 64 KiB shows only Deny on the laptop and is answered at home — nothing should be approved unread — if wrong, a very long command from a laptop-started run can't be approved from the laptop.
47. every pop-up on both ends ignores activation of a non-refusing choice until the guard has passed and the press started after it appeared — Approval Mode is the protection against a steered model, and answers from other devices swap pop-ups under the pointer — if wrong, a fast approver waits under a second.
48. a relative cwd resolves against that machine's project folder for both showing and running, and is a tool error with no folder or an unknown OS — a pop-up showing "." that ran in the home folder is untrue — if wrong, existing habits relying on home-relative cwd get an error telling the model to give an absolute path.
49. non-string command, cwd, path, and file-writing arguments are tool errors on both ends — a JSON-encoded command can execute $(...) — if wrong, a model sending non-text content is told to send text, one extra round.
50. hidden characters show as codes with a one-line warning and "N more lines below" under a box that overflows, and Approve stays available — the person decides, and a block would stop legitimate Unicode in paths — if wrong, a warning some people ignore.
51. ask-unheld joins LOCKED_FRAMES_TO_HOME, carrying only an id, and only stops home counting that laptop for that ask — otherwise a laptop-started run hangs with nothing said — if wrong, page code on a locked laptop can start a 2-minute timer on a question it was asked, which ends in a refusal, not a run.
52. agent-audit.log keeps the first 8 KB and byte count of each long argument — closes Task 12's M4 under ruling 11 — if wrong, the local audit no longer holds whole file bodies written at home.
53. a Deny-only pop-up doesn't count as someone able to approve, so the 2-minute timer runs — otherwise ruling 3's shapes hang — if wrong, a laptop showing a Deny-only pop-up waits out 2 minutes instead of an indefinite wait.
54. a cwd starting with ~ is a tool error asking for an absolute path — ~ means different places per shell and the pop-up must show the real place — if wrong, one extra model round.
55. an omitted replace in apply_patch is an error, an empty string still deletes — item 7 makes apply_patch text fields strings, and an omitted field silently deleting is the kind of surprise ruling 3 forbids — if wrong, one extra model round.
56. pop-up guards judge each activation by its own event timeStamp against the time the pop-up was first painted — a press queued while the page is busy must not count — if wrong, a press during a long draw is ignored and has to be repeated.
57. on Windows a rooted cwd with no drive resolves against the project folder's drive, and is a tool error with no folder — the pop-up must name the real place — if wrong, one extra model round.
58. a pop-up's agreeing choices stay inert until it has been painted, even while the window is minimized — nobody can have read what was never drawn — if wrong, Approve needs the window restored first, while Deny, Escape and the other device still work.
59. the press start comes from pointerdown alone — compatibility mousedown on touch is stamped at the lift — if wrong, an input with no pointerdown can't approve, and every Chromium input sends one.
60. start at login is refused in unpackaged runs, and tests stub it — ELECTRON_RUN_AS_NODE=1 is global here, and a dev login item would start plain Node — if wrong, the owner can't try start-at-login from a dev run.
61. the tray icon appears only while a chat is shared, and closing hides only then — the spec ties hiding to sharing — if wrong, an owner who wants a permanent tray icon doesn't get one.
62. folder paths enter model prompts as JSON.stringify(path), and paths with control characters are refused when chosen (closes Task 12 M7) — laptop folders are hostile text — if wrong, a folder name with a line break must be renamed to use it.
63. a new action set-laptop-folder {path}, checked at home with isChosenFolder, recorded in c.projectFolders under the sender's id and mirrored back; the laptop reads its folder from the mirrored chat, with no separate laptop copy — home already decides the laptop's tool allowlist (spec: folders aren't a boundary on the laptop), so home is the record — if wrong, a hostile home can change the laptop's Run folder, which the Run confirmation shows.
64. **(controller catch)** background throttling stays off always, as at 38df63f — main.js:708 turned it on whenever nothing is shared, reversing a deliberate setting tied to the owner's minimize slowdowns — if wrong, a hidden unshared window uses a little more CPU.
65. **(correction)** at 38df63f the main window used Electron's default (throttled); the false at 627 was the transport window. Keeping the main window unthrottled always is a deliberate change — the chat loop, mirror and laptop tools run in it, and the owner has seen slowdowns when minimized — if wrong, a hidden unshared window uses a little more CPU.
66. every paired laptop may see every device's folder path for a shared project — owner-only, all devices are the owner's — if wrong, one laptop learns another laptop's folder path.
67. a device's folder sets the default only while that device is available for tools, otherwise home — spec line 164 says no folder means home, and an unavailable device must not fail every tool — if wrong, a laptop-folder chat runs commands at home while the laptop's switch is off.
68. single-instance lock per profile, and a second launch shows the first window — a tray-hidden Sanctum makes second launches likely, and two on one profile share the keystore — if wrong, a dev run on the default profile while the owner's Sanctum runs only brings that window forward.
69. every pop-up's guard restarts after the window is shown or restored — frames may run while hidden with throttling off — if wrong, 800 ms more wait after opening Sanctum from the tray.
70. **(replaces part of the round 1 default-device ruling)** a chat whose only folders are on unavailable devices gives a clear tool error for calls without device, and device:"home" needs an absolute path — falling back to home with no folder ran commands in the owner's user folder — if wrong, the model needs one extra round to name home with a full path.
71. "home" is a reserved device name meaning the home PC, and a laptop named "home" gets a suffix — the new error tells the model to use device "home" — if wrong, a laptop the owner named "home" shows as "home (abcd)".
72. a full cwd or path is required at home whenever home has no folder and the chat has one elsewhere, even while that device is available — blank at home would mean the owner's user folder — if wrong, one extra model round.
73. whenever a device argument exists its enum starts with "home", and it's added whenever the chat has a folder on a non-home device — the error must name only values the schema offers — if wrong, tool schemas carry a device argument in more chats.
74. removing a device drops its folder and allowlist entries from every chat — a stale entry kept a "no longer paired" error on every call — if wrong, re-pairing the same laptop needs its folder chosen again.
75. Task 15 splits into 15a (local: Steps 1-3, 7, gitignore, pinned wrangler, relay README runbook, fuses and packaged debug-switch refusal, live-checks list) and 15b (deploy and live checks), which waits for the owner's Cloudflare login and approval — the deploy is an outside action on their paid account — if wrong, 15a's review runs before anything is live.

82. **(replaces Task 14's tray ruling)** while Remote Control is on with a paired laptop, closing hides to the tray on every platform; with no window, an action gets an immediate refusal — spec line 149 — if wrong, a paired home PC stays running after its window is closed until Quit.
